DataMind Twinfold documentation

An open-source governance catalog for two kinds of asset that used to live in different spreadsheets: the business data assets an organisation runs on, and the AI assets — agents, models, endpoints, knowledge bases, MCP servers, tools and prompts — that now read and write them.

Everything in the catalog sits on one set of machinery. An AI agent gets the same detail page, the same change-request workflow, the same approvals, the same audit trail, the same relationship graph and the same Excel export a database table does. Nothing special-cases the AI half.

What DataMind Twinfold is

DataMind Twinfold is a web application that keeps a single, searchable, governed inventory of the things an organisation's data estate is made of, and of the AI that operates on it. It is inspired by the commercial governance suites — Informatica CDGC, Collibra, Axon, Enterprise Data Catalog — with an AI catalog modelled on OpenMetadata 2.0 and Collibra AI Governance, and it is built to be run by a team that does not have an enterprise licence.

Three things make it more than a list:

  • Typed relationships. The catalog records not just that two objects are related but how: a dataset is derived from another, a knowledge base indexes a dataset, an agent retrieves from that knowledge base. Every relationship reads as a sentence in both directions.
  • Governed change. Anyone can ask for a change; only the right people can make one. A relationship touches two objects, so it needs a sign-off from a steward of each side, and the request is refused up front if nobody could ever approve it.
  • A complete history. Every write is captured structurally, by a listener that sits inside the database session rather than by a call someone has to remember to make. The log records who, when, which fields, from what to what, and how the change arrived — through an approval, or by an administrator acting without one.

The problem it solves

Most organisations can answer "what tables do we have?" from a data catalog and "what models are we running?" from a spreadsheet, and cannot join the two. The question that actually matters — which AI systems can reach regulated data, and under whose authority? — falls in the gap.

DataMind Twinfold closes it by making the AI objects first-class catalog entries and giving them edges into the data catalog. Because a knowledge base records the datasets it indexes, and a tool records the tables it reads from, and an agent records the knowledge bases it retrieves from, the answer is a graph walk rather than a week of log archaeology:

Attribute (PII)← indexed into — Knowledge Base← retrieved by — AI Agent
Dataset← read by — AI Tool← used by agent — AI Agent
Dataset← trained on — AI Model← uses model — AI Agent

The same shape answers the questions either side of it: which policies govern an agent, which metric measures its evaluation score, which project delivered it, which business term defines the vocabulary its prompt depends on.

The two catalogs

Seventeen object types, grouped into two catalogs plus one governance record. The grouping is real — it drives the sidebar, the dashboard sections and the node shapes in the graph — but it is only a grouping. Both halves use identical machinery.

People are catalog citizens too

Users are not an asset type — they have no reference number and no change requests — but they have detail pages and they are searchable the same way a dataset is. You look up a steward exactly as you look up a table.

Core concepts

Nine ideas carry the whole product. Everything else is an application of them.

Facet

A facet is one object type, named by its plural route slug — datasets, ai-agents, prompt-templates. The slug is the same word the URL uses, the relationship tables store and the API accepts, so there is one vocabulary end to end. Internally a single registry declares each facet once — its table, its model, its display names, its reference prefix, its containment parent, its search weights — and everything else is derived from it. The application refuses to start if that registry is inconsistent.

Reference number

Every catalog object gets a short, unique, human-quotable identifier on creation: SYS-001, DS-047, AGT-003, MCP-012. People quote these in tickets and meetings, so search treats an exact reference match as almost unbeatable evidence of what you meant, and accepts ds-001, DS 001 and ds1 as the same thing.

Lifecycle status vs domain status

Every object carries a lifecycle status — active, inactive, obsolete — which says whether the catalog entry is current. Several types carry a second status of their own, which says where the thing itself stands: a policy has a policy_status (draft → under review → approved → published → retired), a project has a project_status, a process has an execution_status, and every AI object has an approval_status. An agent can be a perfectly active catalog entry that is still a draft awaiting sign-off.

Data classification

One four-value scale — public, internal, confidential, restricted — used identically on systems, datasets, attributes, policies, agents, knowledge bases and tools. A model endpoint carries a second one, approved_data_classification: the highest class of data allowed through that route, which is what you compare against what the agents using it actually touch.

Steward

A steward is an ordinary user who holds one or more steward roles. There is one steward role per facet — sixteen in total — and a steward may create, edit and delete objects only in the facets they hold, and may approve only change requests targeting those facets. Elsewhere they are a read-only user. A person can hold several roles at once.

Relationship (edge)

A directed, typed link between two catalog objects, drawn from a catalogue of 141 allowed kinds. Each kind declares which facet may sit at each end and what the link is called in each direction, so DS-002 is derived from DS-047 reads back as DS-047 is source for DS-002. Symmetric kinds ("joins to", "same as") read identically both ways and are stored once.

Hierarchy is not a relationship

A dataset belongs to a system; an attribute belongs to a dataset; an endpoint belongs to a model; a tool belongs to its MCP server. That is mandatory structure held as a foreign key, not an optional edge. Hierarchy is shown alongside relationships on the Relationships tab, clearly marked read-only, and is never raised as a change request — you change it by editing the object.

Change request

The route to changing something you cannot change yourself. Any signed-in user can raise one against any object. A steward of the target facet, or an administrator, decides. Requests that create or remove a relationship are different: they touch two objects, so they collect one approval per facet involved and are applied only when none is still pending.

Provenance

Every audit row records how the change arrived: ui for an ordinary edit, cr_apply for the automatic apply step of an approved request, admin_bypass for an administrator acting without one, seed for startup seeding. An administrator shortcut is never indistinguishable from an approved change.

The life of an object

The same path, whichever of the seventeen types you are looking at.

  1. Created — by an administrator or a steward of that facet, through the list page's create button. A reference number is assigned, created_by and updated_by are stamped, and an audit row is written.
  2. Enriched — fields are filled in over time by whoever holds the facet. Anyone else who spots a gap raises a change request instead.
  3. Related — edges are added to other objects. An administrator's edge goes live at once; anyone else's appears immediately on both objects as pending, and turns active when every required side approves.
  4. Governed — policies are attached, metrics measure it, a risk tier and an approval status are set on AI objects.
  5. Audited — every change above is on the object's Audit tab, with the before/after of each field and how the change arrived.
  6. Retired — lifecycle status moves to inactive or obsolete, or the object is deleted. Its audit rows survive it: a record of what happened to something that no longer exists is the whole point of an audit log.

Permission is enforced by the API, not by the interface. The front end hides buttons the current user cannot use, but every write endpoint re-checks the rule itself.

How it is put together

Three technologies, two processes, one directory. The browser talks to one server, and that server talks to a PostgreSQL cluster that belongs to the installation:

Browser→ uvicorn :8080  (/ = built UI, /api = API)— SQLAlchemy → PostgreSQL :55432

There is nothing between the browser and the application — no separate web server, no reverse proxy, and no Node process. The interface is React, compiled once at install time into static files that the same uvicorn process serves at /. One port, one origin, so there is no CORS to configure and TLS is terminated exactly once. The deployed architecture is explained in full on the installation page, including why no Node runs at runtime and a single request traced end to end.

Front end
React 19, TypeScript, Ant Design 6, React Router 7, axios, bundled to static files. Cytoscape with a dagre layout for the relationship graph, lazily loaded so people who never open it never download it.
Back end
FastAPI, SQLAlchemy 2, Pydantic v2 / pydantic-settings, python-jose for JWT, bcrypt for password hashing, openpyxl for the Excel export. Python 3.12+, run by uvicorn with several workers.
Database
PostgreSQL 17 with the pg_trgm extension, generated tsvector columns for full-text search, GIN indexes for both full text and trigram, and a per-table index on upper(reference_number). 26 tables.
Authentication
JWT bearer tokens, HS256, valid for 480 minutes (8 hours). Passwords are stored as bcrypt hashes and are never readable by anyone, administrators included.
Schema management
Created and reconciled at startup, under an advisory lock so several workers cannot race. There is no migration tool yet: create_all, a schema-cleanup pass, and idempotent seeding of steward roles, the first administrator and the relationship catalogue.

What happens when the backend starts

  1. The facet registry is validated — duplicate slugs, a slug too long for its column, a containment parent that is not a facet, a search weight naming a column that does not exist, an enum column placed where only text can go. Any of these and the application refuses to boot, loudly, instead of failing silently later.
  2. Tables are created if they are not there, then a cleanup pass reconciles leftovers from earlier schema shapes.
  3. Search is set up — the generated search_vector column on each table is fingerprinted against its intended definition and rebuilt if the definition changed, then the indexes are ensured.
  4. Steward roles are seeded, one per facet, per facet rather than all-or-nothing, so a facet added later still gets its role.
  5. The default administrator is seeded if no account with that email exists.
  6. The relationship catalogue is seeded — additively, so a type you have relabelled keeps your wording across restarts.
  7. The audit listener is installed on the SQLAlchemy session.

Running it

One command installs it, and one command operates it from then on. Both live in the installation directory and act only on that installation.

Installing

./install.sh               # ask a few questions, then do everything

The installer checks the prerequisites, generates a signing key and a database password, builds the interface, creates its own PostgreSQL cluster inside the installation directory, creates the database and schema, seeds the sixteen steward roles and the 141 relationship types, creates the first administrator, starts the application — and then verifies the result by signing in as that administrator and fetching the interface. Everything it owns is inside that one directory, so deleting the directory removes the installation.

Operating

./dgp status               # is it running, and is it healthy
./dgp start | stop | restart
./dgp logs [app|postgres]  # follow the logs
./dgp health               # ask the running server: readiness and version
./dgp doctor               # binaries, config, database, UI build — all at once
./dgp backup               # pg_dump into var/backups
./dgp passwd <email>       # set a password (there is no UI for this yet)
./dgp help                 # everything else

If the installer generated your administrator password, change it

A generated password is printed once in the installer's summary and written to .env in clear, because the file is written before the account exists. Sign in, run ./dgp passwd <email> to set one you chose, and then blank DGP_ADMIN_PASSWORD — it is read only to seed the first administrator when no administrator exists, so removing it changes nothing about how the platform runs. Create a second administrator too, so one locked-out account is not a crisis.

The API documents itself

With DGP_DOCS_ENABLED on (the installer’s default), the running application serves interactive API documentation at /docs, ReDoc at /redoc and the raw OpenAPI schema at /openapi.json — generated from the code, so it cannot fall out of step with the endpoints. On a default install that is http://127.0.0.1:8080/docs. Turn it off and all three return 404; the routes are not registered at all, not merely hidden.
