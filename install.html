Install and operate DataGovern

Everything between an empty checkout and a running, backed-up, healthy installation — and then the administrator's reference for the questions you actually ask day to day: is it up, where is the log, which process holds that port, how do I check PostgreSQL.

Two things are worth knowing before anything else. First, there are two ways to run this project and they are deliberately different stacks, not one with a switch. Second, a deployment is entirely contained in its own directory — its PostgreSQL cluster, its logs, its backups, its configuration. Deleting the directory removes the installation.

Two ways to run it

Development runs three processes so the code can reload as you type. A deployment runs two, because nothing needs to reload and one fewer moving part is one fewer thing to go wrong.

DevelopmentDeployed
Started withservices/all.sh start./dgp start
Front endVite dev server, port 3000, hot module reload, proxies /api to the backendNo front-end process. Vite is a build step only; the compiled files in frontend/dist are served by the backend
Back enduvicorn, one worker, port 8000, optional --reloaduvicorn, several workers, port 8080 (or 8443 with TLS), serving the API and the interface
DatabaseThe machine's shared PostgreSQL — Homebrew's cluster on 5432Its own cluster inside var/postgres/data on 55432, loopback only
Configuration.env.development, committed to the repository.env, written by the installer, mode 600
Scriptsservices/{postgres,backend,frontend,all}.shdeploy/{postgres,app,cert,all}.sh, driven by ./dgp
Interactive API docsAlways on, at :8000/docsDGP_DOCS_ENABLED, default on, at :8080/docs
Both can run at once, on the same machine

No port overlaps: 3000 / 8000 / 5432 against 8080 / 55432. That is not a coincidence — it is what lets the release build install and test a real copy of itself while you keep working in the development stack.

The two script directories share filenames on purpose

services/postgres.sh and deploy/postgres.sh are different programs. The first drives the machine's Homebrew cluster on 5432; the second creates and drives a cluster inside var/ on 55432. Same five verbs, different database. Check which directory you are typing before you wonder why status says DOWN.

The deployed architecture

Development, for comparison — three processes, two hops:

Browser→ Vite dev server :3000— /api proxy → uvicorn :8000— SQLAlchemy → PostgreSQL :5432

Deployed — two processes, one hop:

Browser→ uvicorn :8080  (/ = built UI, /api = API)— SQLAlchemy → PostgreSQL :55432 (own cluster)

The technologies are identical — React, FastAPI, PostgreSQL. What changes is how they are served.

Vite is two different programs that share one name

This is where the confusion usually is. "Vite" names both a development server and a build tool, and a deployment uses only the second one.

vite — the dev servervite build — the bundler
LifetimeA long-running Node process on port 3000Runs once and exits
What it doesTransforms one .tsx file at a time, on demand, as the browser asks for it. Keeps a WebSocket open so saving a file hot-swaps that moduleFollows every import from index.html, type-checks, tree-shakes, minifies, and writes finished static files to frontend/dist
AlsoActs as a reverse proxy: /api/* → localhost:8000Content-hashes every asset name, so a new build has new filenames
Used in a deploymentNoYes — once, at install time

So after npm run build, Node is not needed at runtime at all. There is no Node process anywhere in a deployed installation. What is left is a handful of ordinary files:

frontend/dist/index.html                             384 B    the page shell
frontend/dist/assets/index-D2VyfNzE.js               1.4 MB   the application
frontend/dist/assets/RelationshipGraph-BUCaXoK2.js   490 KB   the lazily-loaded graph
frontend/dist/favicon.svg, icons.svg

The dev server had two jobs. Only one of them needs replacing.

The dev server's jobWhat happens in a deployment
Serving the HTML and JavaScriptTaken over by uvicorn, through the static mount in backend/app/web.py. It reads bytes off disk and sends them — no compiling, because dist is already finished JavaScript. The dev server was compiling on every request only because the source is TypeScript.
Proxying /api to the backendNothing replaces it — the need disappears. In development the page is on :3000 and the API on :8000, two different origins, and the proxy exists so the browser does not treat the call as cross-origin. In a deployment both are :8080. A relative fetch('/api/…') from a page loaded off 8080 already goes to 8080. There is nothing to forward.
The front-end source code is identical in both cases

It calls /api/… relatively either way. Nothing in frontend/src knows or cares which stack is serving it — only what is in front of it changes. That is why the production work added no front-end code at all.

One process serves the interface and the API

In development the browser talks to Vite, which forwards /api calls to uvicorn. In a deployment there is no Vite: npm run build compiles the application into static HTML, JavaScript and CSS under frontend/dist, and the same uvicorn process that answers /api also serves those files at /. One port, one origin.

Three consequences, each of which removes a class of problem:

  • No CORS. The page and the API come from the same origin, so there is no cross-origin configuration to get wrong, and DGP_CORS_ORIGINS is empty in a normal install.
  • No proxy to keep in step. There is no second server whose route table has to agree with the backend's.
  • TLS is terminated exactly once. Turning HTTPS on is one setting on one listener, not a certificate in two places.

Serving a single-page application from a static mount takes two deliberate behaviours, both in backend/app/web.py:

BehaviourWhy it is needed
A 404 outside /api falls back to index.html/assets/systems/12 and /search?q=x are routes in the React router, not files on disk. Without the fallback, a refresh or a shared link breaks.
A 404 inside /api stays a 404If every miss became a web page, a mistyped endpoint would answer 200 with HTML and the client — expecting JSON — would report something incomprehensible.
index.html is sent no-storeIt is the one file whose name never changes. Cached, a browser keeps loading the old page, which points at asset filenames the new build no longer has.
/assets/* is cached for a year, immutableVite content-hashes every built asset (index-B3kd9x.js), so a new build invalidates them by changing the name.

If the interface was never built, the application does not pretend otherwise: / answers 503 with the command that fixes it, while the API keeps working.

The same request, traced both ways

A browser opens /assets/systems/12 — a route in the React router, not a file on disk:

StepDevelopmentDeployed
1 · Load the page Vite on 3000 has no such file, so it serves index.html and then compiles main.tsx and each import as the browser requests them uvicorn on 8080 looks for assets/systems/12 on disk, does not find it, falls back to index.html, then serves the prebuilt index-D2VyfNzE.js as-is
2 · Render React Router reads the URL and renders the asset detail page. Identical in both.
3 · Fetch the data
/api/assets/systems/12/detail		 → Vite :3000 → proxy → uvicorn :8000 → SQLAlchemy → PostgreSQL :5432 → uvicorn :8080 → SQLAlchemy → PostgreSQL :55432

One ordering constraint follows from this: a mount at / matches every path, so it is registered after every API router. Anything added after the mount would be unreachable.

What else differs in the deployed backend

AspectDeployed behaviour
WorkersSeveral worker processes, so one slow request does not block the rest. The installer picks the count from the machine's CPUs — 1 on two cores or fewer, 2 normally, 4 on eight or more — and writes it as DGP_WORKERS; the scripts fall back to 2 if it is unset. Never combined with --reload: uvicorn's reloader is the supervisor, and the two are mutually exclusive.
Schema bootstrapRuns at startup under a PostgreSQL advisory lock (services/bootstrap.py). Without it, two workers starting together would race on CREATE TABLE.
Connection poolPooled engine with pool_pre_ping (one round-trip per checkout, and a connection the database has since dropped never reaches a request), a recycle window so connections are closed before an idle timeout elsewhere closes them first, and a per-connection statement_timeout of 60 seconds — no single query can run forever.
HealthSplit in two: /api/health is liveness, /api/health/ready touches the database. See health endpoints.
Every response carriesX-Request-ID and a set of security headers. The request id is the hook Phase 2's detailed logging is built on.
Shutdown--timeout-graceful-shutdown 20, so a restart lets in-flight requests finish instead of failing them.
Proxy headers--proxy-headers, trusting X-Forwarded-* only from DGP_FORWARDED_ALLOW_IPS (default 127.0.0.1) — relevant only if you put nginx or a load balancer in front.

And in the database

A deployment does not use the machine's PostgreSQL. It creates its own cluster, inside the installation directory:

var/postgres/data      the cluster itself
var/postgres/socket    its unix socket, so it cannot clash with another server
var/log/postgres.log   its server log

It listens on 127.0.0.1 only, on port 55432. An existing PostgreSQL on 5432 is neither used nor disturbed, and there is no shared cluster whose upgrade breaks this application. The binaries still come from the machine — Homebrew, Postgres.app or a distribution package — and a cluster is bound to its major version, which is why the installer refuses to continue if it finds a version 17 cluster and version 18 binaries.

Like the development stack, it is driven with pg_ctl rather than brew services, so that a stop stays stopped.

Which configuration file is read is not a flag

config.py reads .env if it exists and .env.development otherwise — never both. A chain with one overriding the other reads better and is a trap: a setting the installer happened not to write would be answered by a development default, on a production machine, silently. Two mutually exclusive files cannot do that. The committed development signing key is additionally refused in production by SHA-256 digest, so a published key cannot sign real sessions even if someone copies the file.

The installer checks all of these and stops with the exact command to fix anything missing. On macOS it will offer to run brew install for you; on Linux it prints the right command for your package manager.

Do not run the installer as root

It refuses. PostgreSQL will not start as root, and an install owned by the wrong user is a permissions problem you then have to unpick. Run it as the user who will operate the platform.

Running the installer

From the directory holding install.sh:

./install.sh

It asks a short set of questions, shows you the plan, waits for confirmation, and then does everything: dependencies, the interface build, the PostgreSQL cluster, the database, the schema, the seed data, the first administrator, and a start-and-verify pass. Expect a few minutes, most of it npm ci.

The interview has two paths:

ChoiceWhat you get
1 · DefaultApplication on 127.0.0.1:8080, PostgreSQL on 55432, HTTP, docs enabled. You are still asked for the administrator password.
2 · CustomYou choose the HTTP port, the database port, the bind address, whether to enable HTTPS, whether to expose /docs, and the worker count.

Every port you type is validated as you type it — a non-number, anything below 1024 (which would need root), anything above 65535, or a port already held by another process is rejected with the offending pid named, and it asks again. If the ports are held by a previous install of this platform, it recognises that and offers to stop it and continue.

The administrator password may be one you choose or one it generates. A generated password is printed once, in the summary, and also written to .env — save it at that point.

A single quote cannot appear in the email or password

.env is read by two different parsers — bash and python-dotenv — and single quotes taken literally are the only style both agree on. A value containing ' is refused at the point of entry rather than producing a file that half-parses.

The install verifies itself

The last step does not just check that the port answers. It signs in as the administrator over HTTP and confirms a token comes back, then fetches / to confirm the interface is actually being served. For that login to succeed, the signing key, the database role and password, the schema, the seeded administrator and the password hash must all be right — so one check covers the whole chain.

Binding to 0.0.0.0 exposes the platform to your network

The default is loopback for a reason. If you open it up, turn HTTPS on as well — otherwise passwords and session tokens cross the network in clear text — and narrow DGP_TRUSTED_HOSTS from * to the hostnames the platform is reached by.

What the installer does, step by step

  1. Checking prerequisites — platform, not-root, openssl, curl, uv, Node 20+, the PostgreSQL binaries, the major version of any existing cluster, free disk. It offers to install what it can.
  2. Writing configuration — generates the signing key and the database password with openssl, writes .env at mode 600. An existing .env is only rewritten with permission, and a copy is kept as .env.backup. On a rewrite the existing database password is kept, because the cluster's role already uses it and a new one would simply fail to authenticate.
  3. Installing Python dependencies — uv sync --frozen, falling back to uv sync. Log: var/log/install-uv.log.
  4. Building the interface — npm ci then npm run build. This is the slow step. Log: var/log/install-npm.log.
  5. Setting up PostgreSQL — creates the cluster in var/postgres/data if it is not there, writes the managed block of postgresql.conf, starts it, and creates the database and role. An existing cluster is kept and restarted, not replaced.
  6. Creating the schema — app.cli bootstrap: tables, the search columns and indexes, the sixteen steward roles, the 141 relationship types, and the first administrator. Log: var/log/install-bootstrap.log.
  7. Generating the TLS certificate — only with --https, which is why the step counter reads [n/7] normally and [n/8] with TLS. 825 days, into var/tls.
  8. Starting and verifying — starts the application, waits for readiness, signs in as the administrator, and fetches /.

It is safe to stop and re-run. Nothing in it is destructive: an existing cluster is kept, dependencies are re-synced, the interface is rebuilt, and .env is only rewritten if you say so.

.env is the one file worth protecting

It holds the signing key and the database password, which is why it is mode 600. It is excluded from every release the build script produces, and the build actively searches the staged tree and the git history for its values before packaging. Do not commit it, and do not copy it into a ticket.

Re-running the installer, and upgrading

You want toDo this
Pick up new code in an existing install./dgp rebuild — re-syncs Python dependencies, rebuilds the interface, restarts. It does not touch .env or the database. Schema changes apply themselves at startup.
Change a port, or enable HTTPSEdit .env and ./dgp restart; for TLS, ./dgp https on does both.
Repair a broken install./install.sh again, answering no when it offers to rewrite .env. The cluster and the data are kept.
Start completely fresh, same directory./dgp reset — drops the database and rebuilds it empty. Back up first.
Move an installation to another machineInstall there, then ./dgp restore a dump taken with ./dgp backup. Do not copy var/postgres between machines.
There is no migration tool yet

The schema is created and reconciled at startup — create_all, a cleanup pass, a fingerprint check on the search columns, and idempotent seeding. That handles additions well and does not handle a column that needs rewriting. Take a backup before upgrading across a schema change, and read the startup log afterwards.

Checking the services — a deployed install

Two services, so two things to check. Start with the one command that covers both:

$ ./dgp status
postgres   UP    port 55432  pid 41207  /path/to/install/var/postgres/data
app        UP    port 8080   41284 41285 41286  http  ready

PostgreSQL reporting UP means pg_isready answered — accepting connections, not merely "a process exists". The application lists one pid per worker plus its supervisor.

Read the last column, not just UP. The application reports one of four things, and the difference matters:

It saysMeaningDo this
readyServing, and the database answers. This is healthy.Nothing.
serving but NOT ready (database?)The process is alive but the database is not answering. The failure this split was built to stop hiding../dgp status for PostgreSQL, then ./dgp logs postgres.
port open, not respondingSomething holds the port but is not answering the health check — possibly not this application at all../dgp doctor, then check what owns the port.
DOWNNothing is on the port../dgp start, then ./dgp logs app if it does not come up.

Deeper, in increasing order of thoroughness:

./dgp health        # ask the server: readiness + version
./dgp doctor        # binaries, cluster, .env mode, both services, config, connectivity
./dgp stats         # row counts per table — proves the schema and data are really there

Checking PostgreSQL specifically

deploy/postgres.sh status      # or: ./dgp pg status
./dgp logs postgres            # tail -f var/log/postgres.log
./dgp psql -c 'select version()'
./dgp psql -c '\dt'            # the 26 tables
./dgp stats                    # row counts, via the application's own models

The cluster is found by its own pidfile, var/postgres/data/postmaster.pid, which PostgreSQL maintains itself, and confirmed with pg_isready — so "UP" means accepting connections, not merely "a process exists".

To check it with the machine's own tools, remember the port and the socket are not the usual ones:

pg_isready -h 127.0.0.1 -p 55432
ps aux | grep '[p]ostgres.*var/postgres/data'
lsof -nP -iTCP:55432 -sTCP:LISTEN
A plain psql will not find this database

psql data_governance connects to the machine's PostgreSQL on 5432 — a completely different server, which in a deployment-only setup has no such database. Use ./dgp psql, which supplies the port, the role and the password.

Checking the application specifically

deploy/app.sh status           # or: ./dgp app status
./dgp logs app                 # tail -f var/log/app.log
curl -s http://127.0.0.1:8080/api/health        # alive?
curl -s http://127.0.0.1:8080/api/health/ready  # database answering?
curl -sI http://127.0.0.1:8080/                 # is the interface being served?

With HTTPS on, the port is 8443, the scheme is https, and a self-signed certificate means curl needs -k.

There is no frontend service to check. The interface is files, not a process — so the question "is the frontend up?" becomes "is the build there, and is it being served?":

ls -la frontend/dist/index.html    # does the build exist?
curl -sI http://127.0.0.1:8080/    # 200 and text/html = served
                                   # 503 = no build; run ./dgp rebuild

A missing build is reported rather than hidden: / answers 503 with the command that fixes it, the startup log carries a warning, and deploy/app.sh start warns before it even starts.

Checking the services — the development stack

Three processes here, and one script each. Same five verbs throughout: start, stop, restart, status, logs.

services/all.sh status        # all three at once
services/all.sh start         # postgres → backend → frontend
services/all.sh stop          # frontend → backend → postgres
services/all.sh logs          # tail backend and frontend together
ServiceCheck it withPortIts log
PostgreSQL (Homebrew's cluster)services/postgres.sh status5432$(brew --prefix)/var/log/postgresql@17.log
Backend (FastAPI / uvicorn)services/backend.sh status8000services/logs/backend.log
Frontend (Vite dev server)services/frontend.sh status3000services/logs/frontend.log

By hand, if you prefer:

pg_isready -h localhost -p 5432                     # database
curl -s http://127.0.0.1:8000/api/health            # backend
curl -sI http://localhost:3000/                     # frontend (dev server)
curl -s http://localhost:3000/api/health            # frontend's proxy to the backend
open http://localhost:8000/docs                     # interactive API docs

That fourth line is the one worth remembering. In development the browser reaches the API through Vite's proxy, so checking :8000 directly proves the backend is up but not that the page can talk to it. Checking :3000/api/health proves the whole path.

Three behaviours are shared by every script in both stacks:

  • A service is identified by whoever holds its port, not only by its pidfile. So stop works on a server you started by hand in another terminal, and a stale pidfile can never point the kill at an unrelated process that inherited the number.
  • start is idempotent and waits for genuine readiness — pg_isready, the health endpoint, the port bound — printing the tail of the log if it times out rather than claiming success.
  • stop is SIGTERM, a grace period, then SIGKILL — 15 seconds in the development stack, 20 in a deployment, which also asks uvicorn for a 20-second graceful shutdown so in-flight requests finish. The port is re-checked before success is reported.
If you ever ran brew services start postgresql@17

launchd will restart PostgreSQL after services/postgres.sh stop, so a stop that stays stopped becomes impossible. Unregister it first: brew services stop postgresql@17. Both stacks drive PostgreSQL with pg_ctl deliberately, for exactly this reason.

Development hot reload: DG_RELOAD=1 services/backend.sh restart. (The deployed equivalent is DGP_RELOAD, which drops to a single worker and says so — it exists for debugging an install, not for running one.)

Why this is split, and why it is the check that matters

Early in the project PostgreSQL crashed while uvicorn stayed up, and the only health check kept answering 200 throughout — because it never touched the database. A live process over a dead database is the failure mode most worth catching, so liveness and readiness are now separate questions with separate answers. ./dgp status and ./dgp health both report readiness, not just liveness. If you point a monitor at one endpoint, point it at /api/health/ready.

The single most common support question has an administrative cause

"I got a 403 and I do not know why" is almost always an object type with no steward assigned. An unstaffed type is administrator-only, and it blocks non-administrators from relating anything to it — because a change request nobody could ever approve is refused at the point of asking rather than left to rot. Keep all sixteen types staffed. The People setup guide covers who should hold which role.

Passwords and accounts

Passwords are bcrypt hashes and nobody can read one, administrators included. There is no reset flow in the interface yet, which makes this the escape hatch:

./dgp passwd someone@example.com

It prompts twice without echoing, refuses anything under eight characters, refuses an email it cannot find, and then writes the new hash. There is no way to read the old one. On the development stack there is no dgp, so an administrator recreates the account instead.

TaskHow

Create more administratorsIn the interface, People → Add. Have at least two so nobody is locked out.
Handle a leaverSet the account inactive. Sign-in is refused; their history stays intact. Prefer this to deleting.
Sign everyone out at onceChange DGP_SECRET_KEY and restart. Every existing token becomes invalid.
Assign a Policy, Metric or AI steward rolePUT /api/users/{id} with a steward_facets array — the person form currently lists only six of the sixteen. They work identically once set.
Change the seeded administrator's password before anyone else uses this

admin@datagovern.com / admin123 is a development default that exists so a fresh development database is usable, and it is in the source. A deployment never uses it — the installer asks you for a password or generates one. If you are running the development stack for anything shared, change it.

Backup and restore

./dgp backup                             # var/backups/data_governance-20260926-101500.dump
./dgp backup /elsewhere/before-upgrade.dump
./dgp restore var/backups/....dump       # stops the app, replaces the database, restarts

Custom format, so it is compressed and pg_restore can filter or parallelise it. A restore makes you type the database name to confirm, and stops the application first — a restore over a live schema is a coin toss. Problems are written to var/log/restore.log rather than scrolling past.

What a dump does and does not contain. It holds every asset, relationship, change request, approval and audit record — the whole catalog. It does not hold .env, so keep a copy of your signing key somewhere safe as well: restoring a database with a different DGP_SECRET_KEY works, but signs everyone out.

Back up before

Any upgrade that could change the schema · ./dgp reset · a restore · any bulk edit you are not certain about · moving the installation.

Working in the database

./dgp psql                               # interactive
./dgp psql -c '\dt'                      # the 26 tables
./dgp psql -c 'select count(*) from asset_relationships'
./dgp stats                              # row counts per table, prettier
Two traps if you write SQL against this database by hand

Enum case. SQLAlchemy stores enum names (ACTIVE) while the API returns enum values (active). Raw SQL sees the former, so where status = 'active' matches nothing. Wrap enum columns in lower().

Direct writes are not audited. The audit trail is a listener inside the application's database session. A change made in psql is invisible to it — no author, no before-and-after, no provenance. Use the interface or the API for anything that should have a history, and treat psql as read-only unless you are repairing something.

HTTPS

./dgp https            # is it on?
./dgp https on         # generate a certificate if needed, enable, restart
./dgp https off        # back to plain HTTP, restart
./dgp cert show        # subject, dates, SAN list
./dgp cert --force     # regenerate
./dgp cert csr         # a signing request for your own CA instead

HTTPS is a switch, not a second server. With it on, the listener binds the HTTPS port with the configured certificate and the plain HTTP port is not opened at all — one live URL, never an ambiguous pair. The certificate lives in var/tls and lasts 825 days, which is the maximum most browsers still accept.

A self-signed certificate encrypts the connection, which is what stops a password crossing the network in clear text. What it cannot do is prove identity, so every browser shows a warning and that warning is honest. For one that does not warn, have your organisation's CA sign the CSR, or point DGP_SSL_CERTFILE and DGP_SSL_KEYFILE at a certificate you already have.

The Subject Alternative Name list is the part that matters. Modern browsers ignore the Common Name entirely — a certificate with no SAN entry for the exact host in the address bar is rejected however valid it otherwise is — so every name this server can be reached by is listed. If you start reaching the platform by a new hostname, regenerate.

Starting at login

./dgp autostart on     # launchd on macOS, a systemd user unit on Linux
./dgp autostart        # is it on, and where is the definition
./dgp autostart off
PlatformWhat is writtenInspect it with
macOS~/Library/LaunchAgents/com.datagovernance.platform.plist — RunAtLoad, no KeepAlivelaunchctl list | grep datagovernance, and var/log/autostart.log
Linux~/.config/systemd/user/data-governance-platform.service — a user unit, Type=oneshot with RemainAfterExitsystemctl --user status data-governance-platform, journalctl --user -u data-governance-platform

Two deliberate details. No KeepAlive: the start script launches the services and exits, so launchd would otherwise restart it in a loop forever. And a user unit, not a system one — everything this deployment owns belongs to this user, and a root-owned service writing into a user's home directory is how permissions get broken. On Linux, user services stop when you log out; to run at boot instead, enable lingering:

sudo loginctl enable-linger "$(id -un)"

Cutting a release

build.sh packages the project for someone else to install. It asks where to put the release and remembers the answer for next time.

sh build.sh                     # asks where it goes
./build.sh --out DIR            # answer without asking
./build.sh --version 1.1.0      # set the version everywhere, then build
./build.sh --git                # build and commit, ready to push
./build.sh --test-install       # also install the result for real, then tear it down

The output directory keeps the same path every time, so it can be your local git repository: build, commit, push, add a feature, build again — same folder, same remote, history intact. Only the archives carry a version number.

Three things it insists on, because this is the step where mistakes become public and permanent:

  1. The package is built from an allow-list, never by excluding. An exclude list is a promise that you thought of everything, and the first thing anyone forgets is the thing that leaks. A new file in the working tree is absent from the release until someone adds it to the list.
  2. It refuses to package a secret. The staged tree and the git history — a push sends commits, not files — are searched for private keys, populated credential settings, database dumps, and the literal values in this tree's own .env and .env.development.
  3. It refuses to package something that does not build. The interface is compiled, every Python file byte-compiled and imported, the facet registry validated, and every shell script parsed, before anything is copied. A broken release is worse than no release.

What ships is the application, the deployment scripts, the installer and one README. What stays behind: the development documentation, the design notes, the development service scripts, the sample data and every .env but .env.example. The staging step uses rsync --delete, so it also refuses to write into a directory that already holds something which is not a release of this project.

Uninstalling

  1. Back up first if you might want the data — ./dgp backup, and copy the dump somewhere else.
  2. Turn off autostart — ./dgp autostart off. This is the only thing that lives outside the directory.
  3. Stop both services — ./dgp stop, then ./dgp status to confirm both ports are released.
  4. Delete the directory. The cluster, the logs, the backups and the configuration are all inside it.

Nothing else on the machine is touched. The PostgreSQL, Node and uv installations remain, along with any other cluster on 5432.
