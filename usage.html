Using DataMind Twinfold

A task-by-task guide: get signed in, put a real estate into the catalog, connect the AI half to the data half, and then run the thing day to day — searching, requesting, reviewing and answering audit questions.

For what exists rather than how to use it, see the feature reference. For concepts and architecture, the overview.

First run

  1. Confirm it is up. From the installation directory: 
    ./dgp status     # both services UP, and the application "ready"
./dgp health     # readiness and version, from the running server
    The installer already started it and signed in once to prove the whole chain works, so this is a confirmation rather than a step. If anything is down, ./dgp start, then ./dgp doctor if it does not come up.
  2. Open the application at the address the installer printed — http://127.0.0.1:8080 by default, or https://…:8443 if you enabled HTTPS. ./dgp version prints it if you have forgotten. With a self-signed certificate the browser warns once; accept it.
  3. Sign in as the administrator the installer created — the email you gave it, and the password you chose or it generated. You land on the dashboard with every count at zero.
  4. Set a password you chose, if the installer generated one. 
    ./dgp passwd your.admin@example.com
    It asks twice, does not echo, and refuses anything under eight characters. Then blank DGP_ADMIN_PASSWORD in .env — it is read only to seed the first administrator when none exists, so removing it changes nothing about how the platform runs.
  5. Create a second administrator. People → Add Person → role Admin. One locked-out account should not be a crisis, and there is no self-service password reset in the interface yet.
  6. Take the first backup, and check that you can put it somewhere else: 
    ./dgp backup
    A dump beside the database it protects is not a backup. This is the point to decide where they go and to schedule it.
Before anyone else has the URL

Do steps 4 and 5. Then two more things worth five minutes: if the platform is reachable from the network (DGP_HOST=0.0.0.0), turn on HTTPS with ./dgp https on so passwords do not cross it in clear text, and narrow DGP_TRUSTED_HOSTS from * to the hostnames it is actually reached by. Both are described under configuration.

A button you expected is missing

That is the permission model, not a bug. Create and Edit need administrator rights or the steward role for that specific type; Approve and Reject need the steward role for the target type of that request. Check the user menu for what you hold. Raise Change Request is always available — that is the point of it.

Setting up people

Do this before cataloguing anything, because stewardship decides who can enter data at all, and an unstaffed type quietly becomes administrator-only.

  1. People → Add Person. Fill in name, email and a password, pick the account role — Normal for almost everyone — and add department and job title so they are findable in search.
  2. Assign steward roles in the same form. Give each person the types they genuinely own. Several roles on one person is normal and expected.
    The form currently offers six of the sixteen roles

    System, Dataset, Attribute, Glossary, Project and Process can be assigned from the screen. Policy, Metric and the eight AI roles exist and are fully enforced, but are not yet in the picker — assign those with PUT /api/users/{id} and a steward_facets array such as ["policy","metric","ai_agent","mcp_server"]. Everything downstream treats them identically.

  3. Leave account role as Normal for stewards. A steward is a normal account with steward roles attached. Administrator is a much bigger grant: it bypasses the approval flow entirely.
  4. Check every type has a steward. Any type with nobody assigned can only be edited by an administrator, and — more awkwardly — a non-administrator trying to relate anything to it is refused up front, because nobody could ever approve the request.

What to catalog first

Structure has to exist before what hangs off it. Two required parents dictate most of the order: a dataset needs a system, an attribute needs a dataset, an endpoint needs a model.

Systems→ Datasets→ Attributes→ Glossary→ Policies & Metrics
AI Models→ Endpoints→ MCP Servers→ Tools→ Knowledge Bases→ Prompts→ Applications→ Agents

Agents come last because an agent is mostly a set of relationships to things that must already exist. Relationships come after both passes.

Do not try to be complete on the first pass

Register the objects with their name, owner and classification, then enrich. A catalog of 200 thinly-described objects that are correctly related answers more questions than 40 beautifully-described ones that are not.

Registering data assets

Add a system

  1. Data Catalog → Systems → Create System.
  2. Name it as people say it — "Salesforce CRM", not "sfdc-prod-01". The technical name belongs in the description or the URL, and search will find both.
  3. Pick the system type. Note the three AI-infrastructure types: vector_database for a Qdrant or pgvector cluster, ai_platform, model_gateway for a LiteLLM or similar router. Registering these as systems is what lets a knowledge base later say which system it is stored in.
  4. Set environment and data classification. Classification here is the highest class the system holds.
  5. Fill in owner and technical contact. These are searched at high weight — "who owns X" is a real query.
  6. Set a parent only for genuine platform → component containment.

Add a dataset

  1. Datasets → Create Dataset, and pick the system. This is required; there is no orphan dataset.
  2. Set schema and database names. Weighted highly in search because that is how engineers look a table up.
  3. Choose the dataset type — table, view, file, API endpoint, report or stream.
  4. Set classification, update frequency and retention. Retention is free text so you can write what the policy actually says.
  5. Leave row count approximate. It is a sense of scale, not a metric.

Add attributes

You do not need every column. Catalog the ones that carry meaning or risk: keys, identifiers, anything personal or financial, anything a metric is calculated from, anything a prompt or a tool touches.

  1. Attributes → Create Attribute, and pick the dataset.
  2. Set the data type and length.
  3. Tick primary key and business key separately. The business key is what a person would identify a row by, which is often not the primary key.
  4. Set the classification honestly at this level. This is the field the AI exposure question is answered against — a restricted column is what makes a knowledge base indexing it worth knowing about.
  5. Use sample values and validation rules to say what good data looks like. Sample values are searchable, which is surprisingly useful for finding a column when you only remember what was in it.

Building the glossary

  1. Start with the terms people argue about — "active customer", "churn", "booked revenue". A glossary of undisputed terms is decoration.
  2. Write the definition, then the usage guidelines. The definition says what it means; the guidelines say when to use it and when not to, which is where most disputes actually live.
  3. Fill in synonyms and the abbreviation. Search matches them and then explains itself: a term found through a synonym shows "synonym: …" in the result, so it does not look like a mistake.
  4. Set the domain and the source of definition. "Where did this wording come from?" is the second question anyone asks.
  5. Use the parent term for broader → narrower only. For anything else — synonym of, acronym for, related to, replaces — use a relationship, which is navigable.
  6. Then connect it to the physical world. Add Represents edges to the dataset or column the term is realised by, and Classifies to the columns it labels. That is what turns a word list into a catalog.

Recording policies and metrics

A policy

  1. Policies → Create Policy. Pick the type — including guardrail and ai_ethics, which is how AI guardrails are modelled here.
  2. Set enforcement level. Mandatory, recommended or advisory. Without it a policy is a wish.
  3. Set the policy status separately from the lifecycle status. A policy can be a live catalog entry that is still a draft.
  4. Record the regulation and jurisdiction, and the effective and review dates. The review date is what turns a policy library into a working calendar.
  5. Use the parent field for Policy → Standard → Rule.
  6. Then relate it. A policy that governs nothing governs nothing. Add Governs edges to the systems, datasets, attributes, processes, projects — and any of the eight AI object types — it applies to.

A metric

  1. Write the calculation. This is the reason the record exists.
  2. Set unit, aggregation and grain, so two teams cannot compute it differently.
  3. Set the trend goal. Higher is better, lower is better, or within range — without it, nobody can tell whether the number is good.
  4. Set target, warning and critical thresholds.
  5. Do not look for a "data source" box. There is not one, deliberately. Add Calculated from edges to the datasets and attributes instead — those the catalog can follow when one of them changes.
This is also how you record an AI evaluation

An eval score, a benchmark, a latency budget, a cost-per-call ceiling or a drift monitor is a Metric with a calculation, a target and thresholds, related to the agent, model, endpoint, knowledge base, tool or prompt it scores by a Measures edge. There is no separate evaluation object to learn.

Registering AI assets

Work bottom-up. Each step below only needs things the previous steps created.

1 · AI Models

One row per set of weights you use, including the embedding models. Set provider, family, modality and kind. Put the alias you write in code in version (gpt-4o) and the pinned build a trace reports in resolved version (gpt-4o-2024-08-06) — keeping both is what later answers "which model was actually live in March?". Fill the model-card triad — intended use, limitations, known bias — even briefly; it is the part a regulator asks for and the part that never survives a spreadsheet. Use the parent field only for a model group; a fine-tune's base model is an edge, added later.

2 · Model Endpoints

One row per route, not per model. The same weights served in two regions is one model and two endpoints. Record the serving engine, protocol, auth type, region and — the two that matter most — data residency (where prompts physically go) and prompt retention days (whether the provider keeps them). Set approved data classification: this is the ceiling you will later compare against what the agents using this route actually touch.

3 · MCP Servers

One row per server. Put the reverse-DNS registry name in server name — it is the natural key and is searched at name weight. Set trust status deliberately: anything you have not reviewed belongs in quarantined, not unknown and certainly not approved. Record transport, registry type, scope and auth type.

Never paste a secret into required environment variables

That field takes variable names only, and the launch command must not carry an inline token. Both fields are excluded from every Excel export precisely because they attract pasted credentials — but excluding them from the export does not remove them from the database.

4 · AI Tools

One row per callable thing an agent can bind to, whether or not it comes from an MCP server. Set the tool kind and access mode, and then set the four hints exactly as the server declares them: read-only, destructive, idempotent, open-world. They cost nothing to record and they are the cheapest risk signal you will get. Describe side effects in plain words — "creates a refund", "emails the customer" — and set contains_pii honestly.

5 · Knowledge Bases

One row per retrieval index. Record the store, collection name, embedding dimension, distance metric, chunking strategy, chunk size and overlap, top-k and refresh schedule — enough that someone could rebuild it. Set contains_pii and the classification: this is the field that propagates outward to every agent that retrieves from it. The embedding model and the vector store are relationships, added in the next phase, not fields here.

6 · Prompt Templates

Register prompts that are reviewed, shared or shipped. Put the text in, list the variables, set the role, and set contains_pii and contains_secrets — either being true is a finding. Record who reviewed the wording and when. Agents whose prompt is inline and unreviewed can keep it in the agent's own instructions field instead.

7 · AI Applications

One row per deployable unit — a repo, a service, a product. This is where business accountability sits, so fill in intended purpose and human oversight properly: they are named EU AI Act obligations, and they are asked about the system, not the function. Set the risk tier rather than leaving it unassessed, and record the business and technical owners.

8 · AI Agents

Last, because an agent is mostly relationships. Beyond name and type, three fields carry the governance weight:

FieldWhy it is the one that matters
Autonomy levelDecides whether human-oversight obligations bite. Suggest-only and autonomous are entirely different risk objects.
Acts on behalf ofend_user means data access is scoped to the invoking human. service_account means standing access of its own, which is a far larger blast radius.
SponsorThe accountable human. An agent with no sponsor is nobody's problem until it is everybody's.

Also set the framework, goal, memory type, environment and classification, and attach it to its application if one exists. If not, leave the application empty — that is allowed on purpose, and you can attach it later.

Adding a relationship

  1. Open the object the sentence starts with. Direction matters: a knowledge base indexes a dataset, so start on the knowledge base. If the relationship you want is not offered, you are probably on the wrong end — try the other object.
  2. Relationships tab → Add Relationship.
  3. Choose the relationship. The list only shows kinds where this object is the source, so the same link cannot be created two ways round and read differently on each page. Each option shows what it is called and which type it points at.
  4. Choose the target. The list is filtered to the type that relationship allows, and excludes the object itself. Type to search by name or reference number.
  5. Read the preview. The modal shows the sentence both ways before you commit. If the reverse reads wrong, the relationship is wrong.
  6. Add a note if the reason is not obvious. "Why does this edge exist?" is the question a note should answer.
  7. Submit. The button says Add Relationship if you are an administrator and Raise Change Request otherwise, and the banner above the form tells you which will happen.

What happens next, by who you are

You areResult
An administratorLive immediately, recorded in the audit trail of both objects as an administrator action with no authorising request.
A steward of every type involvedLive immediately, but still recorded as a change request that is implemented at once — so the change keeps its provenance without asking you to approve yourself.
A steward of one sideA change request is raised, your side is pre-approved, and the edge appears dimmed and pending on both objects until the other side's steward agrees.
Anyone elseA change request is raised, awaiting every side. Same pending edge on both objects.
Anyone, but one side has no stewardRefused immediately with a message naming the unstaffed type. Ask an administrator to assign a steward, or to add the relationship directly.
A pending edge is visible on both sides on purpose

The steward on the far side should see a relationship coming, not find one already there. That is why the row is written straight away and shown dimmed with a "Pending approval" chip, rather than being hidden until it is agreed.

Removing a relationship

Use the delete button at the end of the row on the Relationships tab. The confirmation tells you which of two things will happen: an administrator removes it immediately; anyone else raises a removal request, and the edge stays live and marked "Removal pending" until that is approved. An edge already awaiting a decision cannot have a second request raised against it.

Hierarchy rows — under the read-only Hierarchy heading — have no delete button. A dataset belongs to its system as a matter of structure; change it by editing the dataset.

Worked example: which AI can reach this column?

A privacy review asks which AI systems can see customer_email.

  1. Find the column. Type customer_email in the Dashboard search, or paste its reference number. Open it.
  2. Relationships tab. Look at the incoming edges. Anything reading "Indexed into" is a knowledge base that has ingested this column; anything reading "Read by" is a tool that queries it.
  3. Switch to Graph and set depth to 2. One hop shows the knowledge bases and tools; the second hop shows the agents behind them. That picture is the answer.
  4. Open each agent that appears and read three fields: autonomy level, acts on behalf of, and data classification. An autonomous agent acting as a service account is a different finding from a suggest-only agent scoped to the end user.
  5. Follow each agent's endpoint. On the endpoint, check data residency, prompt retention days and approved data classification. If the column is restricted and the endpoint's approved class is internal, you have found a mismatch.
  6. Capture it. From any search — for example type:agent — use Export to Excel to hand the reviewer a workbook with every field, not a screenshot.
  7. Close the loop in the catalog. Raise change requests on whatever needs to change, and attach the governing policy to the objects it applies to with a Governs edge so the same review is faster next time.

Hovering a node dims everything except its neighbourhood, its ancestors and its descendants. Clicking one navigates to it. Depth 1 answers "what touches this?"; depth 2 answers "what touches that?", which is usually where the interesting answer is; depth 3 is for tracing a specific path, not for browsing.

Searching

Two characters starts suggestions. Enter opens the full results page. A few habits pay off:

  • Paste reference numbers. An exact match beats everything else by a wide margin, and ds-001, DS 001 and ds1 all normalise to the same thing.
  • Type badly on purpose. Trigram matching means custmer still finds customer. If everything you are seeing came from fuzzy matching, the page says so.
  • Narrow with type: rather than scrolling. It accepts the words people use — type:agent, type:kb, type:mcp, type:kpi, type:column — not just the route slug.
  • Search enum values directly. quarantined, qdrant, autonomous, vllm and service_account all match.
  • Search people. type:steward or just a name; email addresses match on any fragment, so example.com finds everyone on that domain.
  • Use the chips. Per-type counts sit above the results; clicking one filters without retyping.
  • Watch for "matched on". A glossary term found through a synonym or abbreviation says so, which is often the more useful piece of information.

Exporting to Excel

  1. Search for what you want. Narrow it with type:, status: or the chips first — the export honours exactly what the results page is showing.
  2. Click Export to Excel. The button shows the total, and the file contains all of it, not the page you are on.
  3. Open the workbook. One sheet per object type, every column of the object, relevance order preserved, headers frozen and filters applied. Column headers in red are mandatory fields, read straight from the database's own constraints.

Two things are worth knowing before you circulate one. Names, not internal ids, appear in the created/updated/requested/reviewed columns. And four fields are never in the file: password_hash, the internal search column, and the MCP launch_command and required_env_vars — the last two because they attract pasted credentials and an export leaves the platform.

Raising a change request

This is how anyone gets something changed that they cannot change themselves — and a perfectly reasonable way to propose a change even when you could make it.

  1. Open the object and click Raise Change Request. It is available to everyone, on every catalog object.
  2. Write a title that states the outcome, not the symptom. "Set customer_email classification to restricted" beats "classification wrong".
  3. Pick the change type — update to correct or enrich, create to add something related, delete to retire the object.
  4. Set the priority honestly. Everything high is the same as nothing high.
  5. Explain why in the reason field, and say exactly which fields should change and to what in requested changes. A reviewer who has to guess will bounce it.
  6. Submit. It appears on the object's Change Requests tab and in the Change Requests list, at submitted.

Reviewing one

You can review a request if you are an administrator, or a steward of the target object's type. If the Approve and Reject buttons are absent, you are neither — or it has already been decided.

  1. Open the request from the Change Requests list, from the object's Change Requests tab, or from a search for type:cr status:submitted.
  2. Read the target and the requested changes. The target object is linked at the top; open it in another tab and check the current state.
  3. Approve or Reject. Comments are optional on approval and required on rejection — a rejected request with no explanation just gets raised again.
  4. For a descriptive request, then make the edit. Approving a request that says "set this field to that value" records the decision; it does not type the value in. Open the object and edit it.
  5. For a relationship request, there is nothing else to do. The last approval applies the change itself, in the same transaction, and the request moves to implemented.

Two-sided approvals

A relationship touches two objects with two different stewards, so one approval is not enough. The request carries one row per type involved and is applied only when none is still pending.

SituationWhat you see
Both ends are the same typeOne approval. A dataset-to-dataset edge needs one dataset steward.
You steward one of the two sidesYour side is pre-approved automatically; the request waits on the other. Its status is partially_approved.
You steward both sidesIt is implemented immediately and still recorded as a request, so the change keeps its provenance.
You steward neither sideTrying to review it returns a message naming which type it is waiting on.
Anyone rejectsOne refusal settles it. The request goes to rejected and a pending edge is removed, or a pending removal is cancelled.
An endpoint was deleted while it waitedThe approval is refused rather than recorded as carried out, and you are told why. Re-raise it if the relationship still makes sense.

An administrator can approve any side of any request, which is the unblocking route when a steward is unavailable.

Known gap: the second side is approved through the API, not the screen

The change-request page shows Approve and Reject only while a request is submitted or under_review, and only to a steward of the target type — which for a relationship request is the type at the from end. So once a request reaches partially_approved, and for the steward of the to end, the buttons do not appear even though that person is entitled to decide.

The API accepts it correctly. Until the screen catches up, the second side approves with:

PUT /api/assets/change-requests/{id}/review
{ "cr_status": "approved", "review_comments": "Agreed from the dataset side" }

Everything downstream behaves normally: the edge goes live, the request moves to implemented, and both objects' audit trails record it. An administrator using the buttons is the other way round the problem.

Reading the audit trail

Every object's Audit tab lists what has happened to it, newest first, with a count at the top. Each row shows when, who, the action, a human summary, and — the column people overlook — how.

Chip in the "How" columnMeans
DirectAn ordinary edit made through the application by someone entitled to make it.
Approved changeApplied automatically when a change request was approved. The request's reference is linked next to it.
AdministratorAn administrator acted without a change request. Legitimate, but never silently equivalent to an approved change.
SystemCreated by startup seeding.

Expand any updated row to see the before → after of every field in that edit. Fields that were touched but did not actually change produce no row at all, so the history stays readable.

If you only read the catalog

Your whole toolkit is search, detail pages, the graph and change requests.

  • Start from search, not the sidebar. Paste a reference number, or type a name badly.
  • On an object you care about, read the Overview, then the Relationships tab — the relationships usually say more about what something is than its fields do.
  • When something is wrong or missing, raise a change request. Say what should change and to what. That is the supported route, not a nuisance.
  • Export anything you need outside the tool; you do not need permission for that.

If you are a steward

A weekly rhythm that keeps a catalog honest:

  1. Clear your queue. Search type:cr status:submitted and decide anything targeting your types. A request waiting a week teaches people not to raise them.
  2. Check for pending relationships on your side. Those are edges someone else proposed that are sitting dimmed on your objects.
  3. Look for thin records. Objects in your types with no owner, no classification or no description. Fill them in, or ask whoever knows.
  4. Look for disconnected records. An object with no relationships is an inventory row, not a catalog entry. Ask what it is derived from, what governs it, what it feeds.
  5. Sweep obsolete entries. status:obsolete plus your type; retire or delete what is genuinely gone.

If you are an administrator

  • Keep every type staffed. An unstaffed type is administrator-only, and it silently blocks non-administrators from relating anything to it. This is the single most common cause of "I got a 403 and I do not know why".
  • Use your bypass sparingly. You can add relationships and edit anything directly, and every one of those actions is tagged as an administrator bypass in the audit trail. That is fine for unblocking; it is not a way of working.
  • Unblock stalled requests by approving the waiting side yourself when a steward is away.
  • Review accounts periodically. Deactivate leavers — an inactive account is refused at sign-in while its history stays intact.
  • Passwords are set once from the interface. There is no password field on the edit form and no reset flow yet. On a deployment the escape hatch is ./dgp passwd someone@example.com, which prompts twice and never echoes. Nobody can read an existing password — they are bcrypt hashes.
  • Watch the startup log after any schema change. The application refuses to boot on an inconsistent facet registry, and the message names the problem precisely.

If you run AI governance

A review pass that uses the catalog as it was designed to be used:

  1. Unassessed risk. Search type:agent unassessed, then the other seven AI types. Anything still unassessed has not been looked at.
  2. Autonomy and authority. type:agent autonomous and type:agent service_account. Cross-check each against its application's human-oversight text — an autonomous agent whose application describes no oversight mechanism is a finding.
  3. Untrusted servers in use. type:mcp quarantined and type:mcp unknown; open each and look at the incoming "Used by agent" edges. A quarantined server with live consumers is the one to act on today.
  4. Dangerous tool shapes. Tools with destructive and open-world hints set, bound to autonomous agents. The graph from the tool at depth 1 shows the consumers.
  5. Residency and retention. Every endpoint: check data residency against where you are allowed to send data, and prompt retention days against what you told customers.
  6. Classification ceilings. For each endpoint, compare its approved data classification against the classification of the data the agents invoking it actually reach — follow the knowledge-base and tool edges, do not take the agent's own field on trust.
  7. PII in the wrong places. Knowledge bases with contains_pii set, and prompts with contains_pii or contains_secrets set. The second is always a finding.
  8. Unreviewed prompts. Prompt templates with no reviewer and no review date, and any whose approval status is still draft while the agent using them is live.
  9. Model card gaps. Models with no intended use, limitations or known bias.
  10. Write the findings back. Create the policies, attach them with Governs edges, create the metrics that will measure the gap closing, and raise change requests for the fixes. Then the next review starts from the catalog rather than from scratch.

Starting, stopping and logs

Everything an operator does goes through one command, ./dgp, run from the installation directory. The install and operate guide covers it in full; this is the short version.

./dgp status                 # both services, ports, pids, and whether it is *ready*
./dgp start | stop | restart
./dgp logs [app|postgres]    # follow the logs
./dgp health                 # ask the running server for readiness and version
./dgp doctor                 # the full check when something is wrong
./dgp help                   # everything else

Two services, in dependency order: start brings up PostgreSQL then the application, stop reverses it. That order is not cosmetic — the application's first act is to bring the schema up to date, and stopping the database first would cut it off mid-request. start is idempotent, and waits for genuine readiness rather than reporting success when the port opens.

There is no front-end process — the interface is compiled into frontend/dist and served by the same uvicorn that answers the API, on port 8080. So "is the front end up?" becomes "is the build there, and is it being served?": curl -sI http://127.0.0.1:8080/ — a 200 means yes, a 503 means there is no build and ./dgp rebuild fixes it.

Read the last column of ./dgp status rather than just UP or DOWN. serving but NOT ready means the process is alive while the database is not answering — the failure worth catching, and the reason liveness and readiness are separate questions. See checking the services for what each state means and what to do about it.

Logs live in var/log inside the installation directory: app.log for the application (access lines, tracebacks and startup together) and postgres.log for the database. Nothing rotates them for you.

One directory, one installation

./dgp acts only on the installation it sits in — its own .env, its own cluster in var/postgres, its own ports. If status reports DOWN for something you are sure is running, check which directory you are in before anything else; a second copy installed elsewhere is a completely separate platform with its own database.

Troubleshooting and FAQ

SymptomCause and fix
There is no Create button on a list pageYou are not an administrator and do not hold that type's steward role. Check the user menu; ask an administrator to assign it.
I cannot find the Policy, Metric or AI steward roles in the person formThe picker currently lists only six of the sixteen. The rest are assignable through PUT /api/users/{id} with a steward_facets array; they work identically once set.
Approve and Reject are missing on a change requestYou do not steward the target's type, or the request has already been decided. Administrators can always decide.
"No steward is assigned for X, so this relationship can only be added by an administrator"Exactly what it says: nobody could approve your side. Have an administrator assign a steward for that type, or add the relationship themselves.
"This change request is waiting on a steward of: …"You already decided your side, or you steward none of the outstanding ones. The message names which type is holding it up.
The relationship I want is not in the listYou are on the wrong end of it. The picker only offers kinds where the current object is the source — try the other object. If neither offers it, that pair has no type defined; custom relationship types are on the roadmap.
"That relationship already exists" / "is already awaiting approval"The edge, or its mirror image for a symmetric type, is already recorded. Check the Relationships tab, including dimmed pending rows.
"An object cannot relate to itself"Source and target are the same object. For a genuine hierarchy, use the parent field on the edit form.
A relationship request was refused on approval with a conflictOne of the two objects was deleted, or something else changed, while the request waited. Nothing was recorded as done that was not done. Re-raise it if it still applies.
Search finds nothing for an obvious wordFewer than two characters returns nothing. Otherwise check for a type: token you left in the box — an unrecognised one shows a warning banner naming it.
"No exact match — showing closest matches"Nothing matched on words or reference number, so everything shown came from fuzzy similarity. Usually a spelling difference, occasionally a genuinely absent object.
A dataset will not saveIt needs a system. Likewise an attribute needs a dataset and an endpoint needs a model. Create the parent first.
I cleared a field but it came backAn update leaves out untouched fields rather than nulling them. To genuinely empty a field, save it as blank.
Export gives a file with one "No Results" sheetThe search matched nothing. Widen it or drop a filter.
MCP launch command and env vars are missing from the exportDeliberate. Both are excluded from every export because they attract pasted credentials.
The graph looks empty or truncatedEmpty means no relationships and no children yet. Truncated means the node cap was reached — lower the depth, or start from a more specific object.
I was signed out mid-taskTokens last eight hours; any 401 clears the session. Sign back in — nothing you had saved is lost.
"Account is inactive" at sign-inAn administrator set the account inactive. Ask them to reactivate it.
I forgot a passwordThere is no reset flow in the interface yet, and nobody can read an existing password — they are bcrypt hashes. An administrator runs ./dgp passwd <email> on the server, which prompts twice, refuses anything under eight characters, and refuses an email it cannot find.
The backend will not start and says the facet registry is inconsistentThat guard is intentional and the message names the exact problem. It follows a change to an object type's definition; fix what it names.
The dashboard counts look staleThey are fetched on load. Refresh the page.
The page loads but every panel is empty or errorsThe application is serving while the database is not answering. ./dgp status — if it says serving but NOT ready, check ./dgp logs postgres.
