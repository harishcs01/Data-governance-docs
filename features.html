Feature reference

Everything the platform does, in detail: every object type field by field, every value an enum accepts, all 141 relationship types, how search is scored, how approvals are routed, what the audit trail records and what the API exposes.

If you are looking for how to do something rather than what exists, the usage guide is the companion to this page.

Feature map

AreaWhat you get
Cataloguing17 object types across a data catalog and an AI catalog, each with a full field set, automatic reference numbers, lifecycle status and data classification.
Relationships141 typed, directional relationship kinds out of the box — 55 of them crossing between the data catalog and the AI catalog — each reading as a sentence both ways.
GraphAn interactive neighbourhood view of any object to three hops, with children nested inside their parents, colour by facet, shape by catalog, and honest truncation.
SearchOne box over every type plus people. Ranked full text, typo tolerance, exact reference matching, prefix boost and usage boost, with type: and status: filters and per-type result counts.

AI governanceEU AI Act risk tiers, intended purpose and human oversight, agent autonomy and delegated authority, endpoint residency and prompt retention, MCP trust status, tool behaviour hints, prompt content hashes.

The catalog model

Every object type is declared once in a central facet registry. One registry entry carries the route slug, the database table, the ORM model, the plural and singular display names, the change-request target name, the reference prefix, the catalog group, the containment parent, and the search weighting. Everything else in the product — routes, permissions, audit coverage, the graph's nesting rules, the export's sheet list, the search index definition — is derived from it rather than restated, and a validator refuses to start the application if any of it is inconsistent.

The practical consequence for you: the seventeen types behave identically. There is no feature that works on datasets but not on agents.

Risk tier is the anchor

The EU AI Act tiers are not decoration. An unacceptable-risk system may not ship; a high-risk one needs documented human oversight, evaluation evidence and a conformity assessment. Every other governance decision about an AI object hangs off this field, which is why it defaults to unassessed rather than to something comfortable.

AI catalog

Eight object types covering the AI that runs on your data. They are not a separate product bolted on: same detail pages, same change requests, same dual approval, same audit trail, same graph, same export.

Three modelling decisions shape them, and knowing them makes the field lists read sensibly:

  • Containment is a foreign key; everything else is an edge. An application contains agents, a model contains endpoints, an MCP server contains tools. Delegation between agents, fine-tuning between models and anything crossing into the data catalog is a relationship.
  • There are no version objects. Version, resolved version and content hash are columns on a mutable record. The audit trail already answers "what changed when", so immutable version rows would be busywork until a scanner can populate them.
  • Evaluation is a Metric, guardrails are Policies, vector stores are Systems. Nothing was invented that an existing object type already models.

Two things about a knowledge base are edges, not fields

The embedding model is kb_embedded_with to an AI Model, because an embedding model has its own licence and approval and re-embedding with a different one is a governance event. The vector store is kb_stored_in_system to a System with system_type = vector_database, because a vector database is a data platform, not a new asset class.

The four hints are the cheapest risk signal you have

They are the MCP protocol's own annotations, taken as they come rather than re-invented as a risk scale — which means the server declares them, so they cost nothing to collect. A destructive, non-idempotent, open-world tool bound to an autonomous agent is the shape of an incident, and all five of those facts are in the catalog.

Scanner-ready columns

All eight AI object types carry six extra columns that are inert today. Everything is entered by hand in Phase 1, so source is manual and the rest are empty. They exist now because a future repository scanner upserts on a deterministic identifier, and adding six columns to eight tables later — with no migration tool — is the expensive path.

Relationships

A relationship is a directed, typed edge between two catalog objects. It is stored once and read from whichever object you are looking at, so the same edge reads as "derived from" on one page and "source for" on the other.

Anatomy of a relationship type

PartMeaning
codeThe stable identifier — dataset_derived_from
forward_labelHow it reads from source to target — "Derived from"
inverse_labelHow it reads back — "Source for"
source_facet / target_facetWhich object type may sit at each end. Enforced on write: you cannot point a dataset edge at a policy
is_symmetricTrue when it reads the same both ways ("Joins to", "Same as"). One row, direction resolved at read time
is_systemTrue for the seeded catalogue. Seeded types may be relabelled but never deleted, because edges point at them

Direction follows one convention throughout: the active object is the source, so an edge reads as a sentence with the subject first — "KB-001 indexes DS-004", "POL-002 governs AGT-001".

Rules enforced on every edge

  • The relationship type must exist, and the two facets must match the type's declared ends.
  • An object cannot relate to itself.
  • The same edge cannot be recorded twice; for a symmetric type, the mirror image is the same edge and is also refused.
  • Both endpoints must exist at the moment the edge is written — and again when an approved request is applied, because the world may have moved while the request waited.
  • An edge whose far endpoint has since been deleted is skipped on read rather than rendered as a broken link.

Edge states

StateMeaning
active liveThe relationship exists.
pending_create waitingRequested but not yet approved. The row is written immediately and shows, dimmed, on both objects — so the steward on the far side sees a relationship coming rather than finding it already there.
pending_delete waitingA removal has been requested. The edge is still live until the request is approved.

Each edge also records its provenance: the change request that authorised it, or nothing at all if an administrator created it directly. The Relationships tab shows the difference — a purple change-request chip, or a plain "Direct" chip with the creator's name on hover.

Honest truncation

Three caps keep both the query and the picture bounded, and the view says when one has bitten rather than quietly returning a subset.

CapValueWhy
Maximum depth3Degrees of separation is the cheapest way to bound a traversal.
Maximum nodes250 (default request 150)Beyond this the response is marked truncated and the view says so.
Children drawn per box12A box holding 150 unconnected nodes is a list, not a graph. The rest are summarised as "+N more".
Neighbours per type, per direction, per node12A dataset that 160 others derive from would otherwise be a 3,000-pixel column. "148 more" tells a reader more than 148 identical dots.

The focused object's own children are always drawn, even when no relationship edge reaches them — otherwise a system with twenty datasets and no relationships would render as a single dot while its list view shows twenty rows.

Search

One box searches every object type plus people, on the dashboard. Typing gives suggestions after two characters, debounced, with in-flight requests cancelled so a slow early response can never overwrite a fast later one.

How a result is ranked

Five independent signals, each answering a different question, combined into one score:

SignalQuestion it answersWeight
Full-text rankDoes the text match, and where?× 4.0
Trigram similarity on the nameIs it close even with a typo?× 2.0
Exact reference-number matchDid they paste DS-001?+ 100
Name prefix matchDid they start typing the name?+ 1.5
Click countDo people actually open this one?+ ln(1 + clicks) × 0.5

Full text alone misses typos; trigram alone has no sense of which field matters. Ranking on both and then boosting by real usage is what makes the top result usually the right one.

Field weighting

Within full-text ranking, each object type declares which of its columns matter most. The scheme is the same everywhere, and a hit in an A column outranks one in a D column by roughly ten to one.

WeightMeaningTypical columns
AIdentityname, reference number, glossary abbreviation, MCP server name, KB collection name
BDistinguishing attributesowner, vendor, schema, synonyms, framework, region, model family, agent sponsor
CProsedescription, definition, goal, instructions, intended purpose, template text
DLong tailURLs, SLAs, schedules, examples, schemas, source file paths

Values full text cannot reach

PostgreSQL will not allow an enum cast inside a generated full-text column, so a search for qdrant, quarantined or autonomous could never hit the index however obviously a person would type it. Those columns are matched as plain substrings at query time instead — the same answer already used for email addresses, which full text treats as one atomic token. In practice: searching an enum value works, for every AI object type.

On the results page

  • Per-type chips with counts — filter to one type without retyping. The chip is the same query you could have typed, so one code path serves both.
  • Reference chip and status chip on every hit; people get a purple "person" chip instead of a reference number.
  • A context subtitle per type — the one extra fact that tells two similarly-named objects apart. A system shows its type, a dataset its schema, a knowledge base its vector store, an MCP server its trust status, an agent its type or framework.
  • "Matched on" — when a glossary term was found through a synonym, abbreviation or related term, the result says which, so it does not look like a bug.
  • Fuzzy-fallback notice — when nothing matched on words or reference number and everything shown came from similarity, the page says so rather than pretending.
  • Unknown-filter warning — type:widgets produces a warning naming the token, not a silent literal search.
  • Click logging — opening a result is recorded, which is what feeds the usage boost. Logging never blocks navigation.

What each state means

StateMeaning
submittedRaised, nobody has looked yet.
under_reviewBeing considered.
partially_approvedSome, but not all, required sides have approved. Only relationship requests can reach this state.
approvedAgreed. For a descriptive request this is the end state — a human then makes the edit.
rejectedDeclined, with comments. One refusal settles a multi-sided request; there is no point collecting the rest.
implementedCarried out. A relationship request reaches this automatically the moment the last approval lands — the decision and its effect share one transaction, so a request can never read "approved" while the catalog disagrees.

Approval routing

A single-object request needs one decision, from a steward of the target's type or an administrator.

A relationship request touches two objects with two different stewards, so one approval is not enough. The request carries one approval row per facet involved, and is applied only when none is still pending. Four rules make that workable:

  1. Both ends the same type collapses to one approval. A dataset-to-dataset edge needs one dataset steward, not two.
  2. A side the requester already stewards is pre-approved. Making someone approve their own request adds a click and no scrutiny.
  3. If the requester stewards every side, it is implemented immediately — but still recorded as a change request, so the change keeps its provenance.
  4. If any side has no steward at all, a non-administrator is refused up front, with a message naming the unstaffed type. A request nobody could ever approve is better refused at the point of asking than left to rot in a queue.

When an approved relationship request is applied, the edge is re-validated first. If an endpoint was deleted while the request waited, the edge is dropped and the reviewer is told; if anything else has changed underneath, the approval is refused rather than recorded as carried out when it was not.

Known gap between the API and the screen

The API routes multi-sided approvals correctly: it works out which pending sides the reviewer may speak for, records their decision against each, and applies the change on the last one. The change-request page is narrower — it shows Approve and Reject only while the request is submitted or under_review, and only to a steward of the request's target type, which for a relationship request is the facet at the from end. A request sitting at partially_approved, or one awaiting the to end's steward, therefore shows no buttons to the person entitled to press them. Until the page catches up, that side approves via PUT /api/assets/change-requests/{id}/review, or an administrator decides it.

Audit trail

Auditing is structural. A listener sits inside the database session and diffs everything about to be written, so a new endpoint is audited whether or not whoever wrote it remembered to call anything. The alternative — an explicit helper call in each of the forty-odd write paths — is one forgotten line away from a silent hole in the trail.

RecordedDetail
object_type / object_idWhat was touched. A deliberately generic pointer, so a row survives the deletion of the thing it describes
actioncreated updated deleted relationship_added relationship_removed relationship_proposed
field_changesFor an update: every field that actually changed, with its old and new value. Fields that were touched but unchanged produce no row at all
summaryA human one-liner, so the interface never has to reconstruct meaning from a diff
performed_by / performed_atWho and when. The acting user is captured from the request itself, before any dependency runs
viaui · cr_apply · admin_bypass · seed
source_cr_idThe change request that authorised it, where there was one

Three details worth knowing:

  • Noise is excluded. created_at, updated_at, search_vector and password_hash never appear in a diff.
  • A relationship is recorded against both endpoints. Without that, the far object's history would be silent about something that visibly changed its page.
  • An administrator shortcut is never silently equivalent to an approved change. The Audit tab shows it as an orange "Administrator" chip, with a green "Approved change" chip and a link to the request for the other case.

Each object's Audit tab paginates newest-first and expands any row to show the before → after of every field in that edit.

One convention to know if you call the API directly

Enum fields are sent and received as their lower-case values — "lifecycle_status": "active", "trust_status": "quarantined" — not as internal names. On update, a field you omit keeps its current value rather than being cleared.

Some things are absent on purpose, because an existing object type already models them:

Known gaps, tracked in the project roadmap: there is no migration tool yet (the schema is created and reconciled at startup); there is no repository scanner yet, which is what the scanner-ready columns are waiting for; steward assignment is per type rather than per object; metric values over time are not stored, only metric definitions; and bulk import, custom relationship types, policy compliance reporting, dashboard analytics and notifications are planned rather than present.
